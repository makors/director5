# Director independent UI review

Review date: 2026-10-03. Reviewer: Codex independent UI review agent. Claude/Opus was **not** used; no callable Claude/Opus MCP or CLI is available. This is a prepared review and handoff, not approval from the requested Opus reviewer. No application source was changed.

## Goal and scope

Polished, restrained SaaS usability inspired by Vercel's light interface, while keeping Director's original blue **#087cfc**. Director should remain simple to use like tjcsl/director4, with its existing features retained. Header identity is the word **Director** only; no added logo. Account trigger shows the person's full name with no arrow. Changes are limited to UI templates, CSS, and UI interaction behavior; no authentication, backend behavior, deployment, or secrets.

## Evidence

Fresh screenshots were captured from the current static export `the isolated sample preview export`, served only on loopback, at 1440×1000 desktop and 390×844 mobile. Files/editor and the open administrator account menu were captured as separate states. Screenshots are under `screenshots/`; see `screenshot-manifest.md`. Numerous older parity/redesign images were also viewed for comparison, but findings below use the fresh set. The current preview already meets text-only branding and arrow-free full-name account requirements; older images with `Account` + a triangle are stale.

The local home page loaded with meaningful content, expected controls, no framework error overlay, and no reported browser errors. This is a visual UI review, not verification of live backend features. Static sample constraints are described in the preview banner.

## Judgment

The interface has a sound restrained base: readable Geist type, sensible page width, thin borders, working full-name menu, desktop file/editor split, and useful feature parity. It currently looks unfinished because headings, body text, state, and action groups share nearly the same weight. Some pages have spacing collisions and inconsistent site identity. More deliberate grouping and visible Director blue will improve it without adding decorative dashboards or removing features.

## P0 — address before presenting the UI as finished

1. **Restore Director blue deliberately.** `static/tailwind/input.css` currently makes primary buttons, active tabs, progress, and radios neutral black, and uses Vercel blue `#0070f3` for focus. Add `--dt-brand: #087cfc`, a pale tint such as `#eef6ff`, and a darker text/action shade such as `#066bd7`. Use the exact original blue for active underline, progress, focus, and selected outlines. Use the darker shade for white-label primary buttons and small text links: white on exact #087cfc is 3.96:1, while white on #066bd7 is 5.13:1. The original blue remains the identity color. Keep secondary buttons white/neutral and destructive actions red. Avoid recoloring all text blue.

1. **Give site pages one consistent identity header.** Overview, Files, and Settings show site name/status/domain, but Database uses a tiny 14px `Database` heading and back link; Terminal uses an extra `robotics-club / Terminal` line and a separate header arrangement. Reuse the existing `.dt-project-header` structure on Database, Terminal, Logs, SSH, and SQL views; put the page title below the same site tabs. A small shared header partial avoids future drift. Preserve every action and route. Sources: `templates/sites/databases/detail.html`, `templates/sites/runtime/{terminal,logs,ssh}.html`, query template, and current header in `templates/sites/settings.html`.

1. **Fix section spacing and heading hierarchy.** Database's SQL buttons directly touch `Password`; `Rotate password` touches `Delete database`. Images' `Add image` button touches `Base images`; image configuration's submit button touches `Available images`. Place sibling sections in a wrapper with 24px gap, give section h2 16px/600 and 12–16px below, and give form/action footers 20–24px separation from the next section. Keep h1 at 24–26px/600. Scope selectors to content sections; don't globally add margins to every paragraph or table cell.

1. **Keep the active mobile tab visible.** On Settings mobile, the selected `Settings` tab is partly clipped off the right edge. Keep horizontal tabs and every feature, but scroll the current tab into view on load and add a small right-edge scroll cue when more tabs exist. All tab hit areas should remain 44–48px. At 390px the user should be able to identify their current section immediately; do not force them to discover the active tab by swiping.

## Shared visual rules

- Background stays #fafafa; content surfaces white, text near #171717, muted text around #666, borders #e5e5e5. Keep local Geist fonts; do not introduce another type family.
- Use 6px controls, 8px content panels, 16/20/24px spacing. No gradients, glow, giant hero blocks, decorative icons, fake KPI cards, excessive shadows, or marketing copy.
- Borders establish groups; use at most a modest menu/dialog shadow. Screens should have 2–4 meaningful groups, not a card around every label.
- Desktop controls 36–40px; mobile controls at least 44px. Inputs remain 16px on mobile to avoid browser zoom.
- Blue marks a selected section or key action; semantic green/amber/red mark real states with accompanying text. Color never becomes the only state indicator.
- Keep existing warnings, helper text that explains actual consequences, permissions, technical details, and complete feature navigation. Simplification means clearer presentation, not hiding or deleting capabilities.
- The preview disclosure is useful but occupies much of the mobile first screen. A concise collapsed summary with the full limitations expandable is an optional preview-only polish; keep role-switch links and all limitations accessible.
